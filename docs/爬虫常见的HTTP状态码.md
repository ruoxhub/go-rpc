# 爬虫常见的反爬状态码与应对方案

在爬虫开发中，目标网站常通过返回特定的 HTTP 状态码来识别并拦截自动化请求。掌握这些状态码的含义及应对策略，是绕过反爬、保障数据稳定采集的关键。

---

## 一、常见反爬状态码速查表

| 状态码 | 名称 | 反爬含义 | 常见应对 |
|--------|------|----------|----------|
| 401 | Unauthorized | 需要登录/Token 认证 | 携带 Cookie、Token、Basic Auth |
| 403 | Forbidden | 服务器拒绝（封 IP、封 UA、鉴权失败） | 换 UA、换 IP、带合法 Cookie |
| 407 | Proxy Authentication Required | 代理需要认证 | 配置代理用户名密码 |
| 429 | Too Many Requests | 请求频率过高被限流 | 降速、退避重试、用代理池 |
| 503 | Service Unavailable | 服务暂不可用（常为反爬盾） | 重试、过验证码、模拟浏览器 |
| 301/302/307/308 | 重定向 | 跳转到验证页/登录页/拦截页 | 跟随或停止，处理验证 |
| 200 | OK（异常） | 返回假数据/验证码/空页面 | 校验内容、识别验证码 |
| 404 | Not Found | 伪装不存在（实际为拦截） | 确认接口是否失效 |
| 502/504 | 网关错误 | 网关限流或过载 | 重试、降低并发 |

---

## 二、各状态码详解与应对方案

### 1. 401 Unauthorized（未授权）
**原因**：接口要求身份认证（登录态、API Token、OAuth 等），请求未携带或携带错误。

**应对**：
- 抓取登录后的 `Cookie` 并持久化（注意过期时间）。
- 在请求头中加入 `Authorization: Bearer <token>` 或 `Basic` 认证。
- 优先使用官方 API 的 `access_token`，避免模拟登录。

### 2. 403 Forbidden（禁止访问）
**原因**：最常见的反爬码。服务器识别出非浏览器特征（UA、Referer、头缺失）、IP 被封、或权限不足。

**应对**：
- **伪造请求头**：补全 `User-Agent`、`Referer`、`Accept`、`Accept-Language` 等。
- **随机化 UA**：从 UA 池中随机选取，模拟多浏览器。
- **换 IP**：使用代理池 / 高匿代理轮换出口 IP。
- **带合法 Cookie**：维持登录态，避免被判定为匿名爬虫。
- **降低频率**：配合 429 策略一起处理。

```python
headers = {
    "User-Agent": random.choice(UA_POOL),
    "Referer": "https://www.example.com/",
    "Accept": "text/html,application/xhtml+xml,*/*;q=0.8",
}
```

### 3. 407 Proxy Authentication Required（代理需要认证）
**原因**：使用的代理服务器要求用户名密码认证，但请求未提供。

**应对**：
- 在代理 URL 中携带凭据：`http://user:pass@host:port`。

- 或在请求头加入 `Proxy-Authorization`。
- 检查代理是否到期、白名单 IP 是否配置正确。

### 4. 429 Too Many Requests（请求过于频繁）
**原因**：触发了频率限制（Rate Limit），是限流型反爬的核心信号。`Retry-After` 响应头常给出建议等待秒数。

**应对**：
- **限速**：用 `time.sleep()` 或令牌桶/漏桶算法控制 QPS。
- **指数退避重试**：收到 429 后按 `2^n` 秒递增等待再重试。
- **分布式代理池**：将请求分散到多个 IP。
- **读取 `Retry-After`**：尊重服务端建议的冷却时间。

```python
import time, random
def fetch(url, session, retry=3):
    for i in range(retry):
        r = session.get(url)
        if r.status_code == 429:
            wait = int(r.headers.get("Retry-After", 2 ** i)) + random.random()
            time.sleep(wait)
            continue
        return r
    return None
```

### 5. 503 Service Unavailable（服务不可用）
**原因**：常出现在反爬盾（如 Cloudflare、Akamai）背后，表面是"暂时不可用"，实际是触发了人机验证或 IP 风控。

**应对**：
- **Cloudflare 5 秒盾**：返回 JS 挑战页，需执行 JS 计算 `cf_clearance`。可用 `playwright`/`puppeteer` 真实浏览器绕过，或借助 `cloudscraper` 库。
- **识别验证码**：检测页面是否含验证码，接入打码平台或人工识别。
- **重试 + 换 IP**：短暂冷却后更换出口 IP 重试。
- **模拟浏览器指纹**：启用 `headless=False`、加载真实 TLS 指纹（如 `curl_cffi`）。

### 6. 3xx 重定向（301/302/307/308）
**原因**：被重定向到登录页、验证码页、地区拦截页或"访问过于频繁"提示页。

**应对**：
- **关闭自动跳转**（`allow_redirects=False`）观察 `Location` 头，判断被引到哪里。
- 若跳登录页 → 补充 Cookie；若跳验证页 → 处理验证码。
- 注意 302 到同一域名的不同子域可能是 Session 校验。

### 7. 200 OK 但内容异常（最隐蔽的反爬）
**原因**：状态码正常，但返回的是**假数据、空列表、验证码页或"请验证"提示**，用于消耗爬虫算力、误导采集结果。

**应对**：
- **内容校验**：检查返回体是否含预期字段/关键词，或长度是否异常。
- **验证码识别**：用 OCR / 机器学习 / 第三方打码平台处理。
- **行为校验**：补齐全量请求头、Cookie、必要时用浏览器渲染。
- 设置"异常数据"告警，发现 200 却无数据立即排查。

### 8. 404 Not Found（伪装拦截）
**原因**：部分站点对爬虫请求返回 404，而真实浏览器能正常访问，属于"软拦截"。

**应对**：
- 用浏览器对比同一 URL 的返回，确认是否真失效。
- 补请求头、换 UA、带 Cookie 后再试。
- 检查是否触发了参数签名校验（如缺失 `sign`、`token`）。

### 9. 502 / 504（网关/网关超时）
**原因**：多为高并发压垮网关或网关层限流，也可能是反爬的"软拒绝"。

**应对**：
- 降低并发数，增加请求间隔。
- 重试（配合退避），优先换可用节点。
- 监控成功率，区分"真故障"与"被限流"。

## 三、通用反爬工程化策略

1. **请求头工程**：随机 UA、完整 Header、合理 `Referer` 与 `Accept` 链。
2. **IP 代理池**：高匿代理 + 健康检查 + 自动剔除失效节点。
3. **Cookie 池**：多账号登录态轮换，避免单账号风控。
4. **限速与退避**：令牌桶限速 + 指数退避重试，尊重 `Retry-After`。
5. **浏览器指纹模拟**：`playwright`/`curl_cffi` 还原真实 TLS、JS 执行环境。
6. **验证码体系**：OCR、打码平台、或滑块/点选的人机验证破解。
7. **状态码监控**：对每种状态码做统计与告警，快速定位反爬升级。

---

## 四、状态码判断优先级建议

```
收到响应
  ├─ 401/407 → 补认证/代理凭据
  ├─ 403     → 换 UA / 换 IP / 带 Cookie
  ├─ 429     → 降速 + 退避重试
  ├─ 503     → 过盾/验证码 + 换 IP
  ├─ 3xx     → 看 Location，处理登录/验证跳转
  ├─ 200     → 校验内容真实性（防假数据）
  └─ 404/5xx → 对比浏览器，判断是否软拦截
```
