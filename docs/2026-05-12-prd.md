策略模式 (Transport 接口)

  MCP SDK 的 Transport 抽象是教科书级别的策略模式：

  type Transport interface {
      Connect(ctx context.Context) (Connection, error)
  }

  type Connection interface {
      Read(context.Context) (jsonrpc.Message, error)
      Write(context.Context, jsonrpc.Message) error
      Close() error
      SessionID() string
  }

  对比 sekiro-go 当前状态：WebSocket 通信逻辑直接耦合在 pkg/server/websocket/handler.go 中，没有传输层抽象。如果未来要支持 gRPC、QUIC 或纯 TCP，需要大量重构。

  借鉴建议：为 sekiro-go 抽象一个 Transport 接口，将 WebSocket 作为一种实现。这样可以在不改动业务逻辑的情况下支持新的传输协议。

  ---
  责任链模式 (Middleware)

  type MethodHandler func(ctx context.Context, method string, req Request) (Result, error)
  type Middleware func(MethodHandler) MethodHandler

  分为 Sending/Receiving 两条链，职责清晰。

  对比 sekiro-go：当前中间件仅有 CORS 和 Auth，且只作用于 HTTP 层（Gin 中间件）。WebSocket 消息处理没有中间件机制，扩展性差。

  借鉴建议：在 pkg/server/websocket 层引入消息级中间件链，支持日志、限流、认证等横切关注点。结构可以简化为：

  type MessageHandler func(ctx context.Context, msg *protocol.Packet) error
  type MessageMiddleware func(MessageHandler) MessageHandler

  ---
  观察者模式 (功能变更通知)

  MCP SDK 的 changeAndNotify 机制（10ms 去抖）在功能注册/注销时自动通知所有 session。

  对比 sekiro-go：当前 pkg/eventbus 已有事件总线，但没有去抖机制，也没有用于客户端状态同步。

  借鉴建议：在 ClientManager 的分组变更、设备上下线事件中引入去抖通知，避免高频变更时产生通知风暴。

  ---
  需要调整后使用的

  泛型 featureSet

  MCP SDK 用 featureSet[T] 管理 tools/prompts/resources，支持惰性排序和迭代器分页。

  sekiro-go 的 ClientManager 用 sync.Map + 手动遍历管理分组和客户端。泛型集合可以统一管理逻辑，但 sekiro-go 的场景更侧重并发安全和路由选择，不能直接照搬。

  借鉴建议：提取一个泛型的 ConcurrentRegistry[K, V]，封装 sync.RWMutex + map，提供 Add/Remove/Get/Iterate/Count 方法，替代散落各处的 map 操作。

  ---
  模板方法 (connect 泛型函数)

  func connect[H handler, State any](ctx context.Context, t Transport, b binder[H, State], ...) (H, error)

  Client 和 Server 共享连接生命周期管理。sekiro-go 的客户端和服务端连接管理逻辑完全独立，存在重复代码。

  借鉴建议：抽象连接生命周期为 ConnectLoop，统一处理重连、心跳、优雅关闭。

  ---
  2. API 与接口设计

  值得直接复用的

  泛型工具注册 (编译时类型安全)

  func AddTool[In, Out any](s *Server, t *Tool, h ToolHandlerFor[In, Out])

  自动推断 Schema、自动验证参数、自动序列化输出。消除了运行时类型断言错误。

  对比 sekiro-go：pkg/server/api/handlers.go 中每个 handler 手动解析参数、手动构造响应，重复代码多且容易出错。

  借鉴建议：设计一个泛型 handler 注册器：

  func RegisterAPI[Req, Resp any](router *gin.RouterGroup, method, path string, handler func(ctx context.Context, req Req) (Resp, error))

  内部自动处理：参数绑定 → 校验 → 调用 handler → 统一响应格式 → 错误处理。

  ---
  统一的 Params/Result 类型体系

  MCP SDK 为每个 RPC 方法定义了明确的 XxxParams 和 XxxResult 类型，而非 map[string]any。

  对比 sekiro-go：invoke API 使用 map[string]any 传递参数，类型安全性差。

  借鉴建议：为核心 API 定义强类型请求/响应结构体，配合 binding:"required" 标签做校验。

  ---
  分页迭代器

  func (cs *ClientSession) Tools(ctx context.Context) iter.Seq2[*Tool, error]

  客户端无需关心分页细节，自动翻页。

  借鉴建议：在 sekiro-go 的管理 API（设备列表、日志列表、指标列表）中引入类似的分页封装，避免每个 handler 重复实现分页逻辑。

  ---
  需要调整的

  错误码体系

  MCP SDK 的错误码分散在多处（文档中也指出了这个问题），但其 JSON-RPC 标准错误码 + 自定义业务错误码的分层思路值得借鉴。

  sekiro-go 当前错误处理：直接返回 HTTP 状态码 + 字符串消息，没有业务错误码。

  借鉴建议：定义统一的错误码体系：

  type AppError struct {
      Code    int    `json:"code"`    // 业务错误码
      Message string `json:"message"` // 用户可见消息
      Detail  string `json:"detail"`  // 调试信息（仅 debug 模式）
  }

  ---
  3. 性能优化技巧

  值得直接复用的

  JSON Schema 缓存 (schema_cache.go)

  MCP SDK 缓存了工具的 InputSchema/OutputSchema 推断结果，避免每次请求都做反射。

  对比 sekiro-go：每次 invoke 请求都重新解析参数，没有任何缓存。

  借鉴建议：对于固定结构的请求（如 Action 定义），缓存其验证器实例。可以用 sync.Once 或 sync.Map 实现。

  ---
  去抖通知 (10ms debounce)

  高频变更合并为一次通知，减少网络开销。

  对比 sekiro-go：设备上下线时立即广播，高并发场景下可能产生通知风暴。

  借鉴建议：在 pkg/server/client/manager.go 的 Register/Unregister 中引入去抖：

  type debouncer struct {
      timer    *time.Timer
      mu       sync.Mutex
      duration time.Duration
  }

  ---
  高性能 JSON 编解码 (segmentio/encoding)

  MCP SDK 使用 github.com/segmentio/encoding 替代标准库 encoding/json，性能提升 2-5x。

  对比 sekiro-go：使用标准库 encoding/json。

  借鉴建议：在协议层（pkg/protocol）的序列化热路径中，可以考虑引入 github.com/bytedance/sonic 或 github.com/goccy/go-json 作为 drop-in 替换，零改动获得性能提升。        

  ---
  需要评估后决定的

  KeepAlive 心跳机制

  MCP SDK 支持配置化的心跳间隔。sekiro-go 已有心跳包（HEARTBEAT type=0），但间隔硬编码。

  借鉴建议：将心跳间隔移入 config.yaml，支持运行时调整。

  ---
  异步请求处理 (jsonrpc2.Async)

  MCP SDK 支持标记请求为可并发处理，避免阻塞读循环。

  对比 sekiro-go：WebSocket 消息处理在单个 goroutine 中顺序执行。

  借鉴建议：对于耗时的 invoke 请求，应该在独立 goroutine 中处理，避免阻塞同一连接上的心跳和其他消息。当前 forwarder 已经做了异步转发，但消息解析阶段仍是同步的。

  ---
  4. 测试与质量保障

  值得直接复用的

  InMemoryTransport (测试专用传输)

  func NewInMemoryTransports() (Transport, Transport)

  创建一对内存管道，无需启动真实服务器即可测试完整的 Client-Server 交互。

  对比 sekiro-go：测试需要启动真实的 HTTP 服务器和 WebSocket 连接，测试慢且不稳定。

  借鉴建议：为 sekiro-go 实现一个 InMemoryTransport，用于单元测试中模拟客户端注册、invoke 调用等流程。这是提升测试覆盖率最有效的手段。

  ---
  一致性测试 (conformance tests)

  MCP SDK 有独立的 conformance/ 目录，验证实现是否符合协议规范。

  对比 sekiro-go：没有协议级别的一致性测试，只有零散的单元测试。

  借鉴建议：编写一组协议一致性测试，验证数据包编解码、心跳响应、注册流程等核心协议行为。放在 pkg/protocol/conformance_test.go 中。

  ---
  版权头检查测试 (copyright_test.go)

  自动化检查所有源文件是否包含正确的版权头。

  借鉴建议：如果项目有开源计划，可以引入类似的自动化检查。对于内部项目，可以改为检查文件头注释规范。

  ---
  需要调整的

  测试数据管理 (testdata/ 目录)

  MCP SDK 将测试用的 JSON fixtures 放在 testdata/ 目录中，Go 工具链会自动忽略这些目录。

  对比 sekiro-go：测试数据散落在测试文件中，或者直接硬编码。

  借鉴建议：在 pkg/protocol/testdata/ 中放置标准的数据包二进制样本，用于回归测试。

  ---
  5. 文档与可维护性

  值得直接复用的

  分层文档结构

  README.md          → 项目介绍（自动生成）
  CONTRIBUTING.md    → 贡献指南
  AGENTS.md          → AI Agent 开发指南
  SECURITY.md        → 安全策略
  ROADMAP.md         → 路线图
  design/            → 设计文档
  docs/              → 生成的功能文档
  examples/          → 示例代码

  对比 sekiro-go：只有 CLAUDE.md（给 AI 用的）和 README，缺少面向人类开发者的文档。

  借鉴建议：
  - 添加 CONTRIBUTING.md（贡献指南）
  - 添加 docs/architecture.md（架构决策记录）
  - 丰富 sample/ 目录的示例代码

  ---
  自动生成文档 (internal/readme, internal/docs)

  MCP SDK 通过 go generate 自动从代码生成 README 和 API 文档，保证文档与代码同步。

  借鉴建议：使用 swaggo/swag 从 Gin handler 的注释自动生成 Swagger/OpenAPI 文档。sekiro-go 有大量 HTTP API，手动维护文档容易过时。

  ---
  AGENTS.md (AI 开发指南)

  专门为 AI 辅助开发提供的上下文文件，这正是 sekiro-go 的 CLAUDE.md 已经在做的事情。MCP SDK 的做法更通用（不绑定特定 AI 工具）。

  借鉴建议：当前 CLAUDE.md 已经很完善，可以考虑拆分为 CLAUDE.md（AI 专用指令）+ DEVELOPMENT.md（通用开发指南），让非 AI 开发者也能受益。

  ---
  需要调整的

  模块路径与版本管理

  MCP SDK 使用 github.com/modelcontextprotocol/go-sdk 作为模块路径，子包通过 mcp/、auth/、oauthex/ 组织，职责边界清晰。

  对比 sekiro-go：使用 github.com/mrh30000/go-rpc，pkg/ 下的包划分基本合理，但 pkg/server/ 下的子包过多（api, client, detector, flow, forwarder, handlers, middleware,   
  router, websocket），部分包只有 1-2 个文件。

  借鉴建议：考虑合并小包。例如 flow 和 forwarder 可以合并为 dispatch，detector 可以并入 websocket。减少包数量，降低导入复杂度。
